# MUSE 自主策略发现系统实施方案（v1.1）

> 状态：方案设计稿，提请人工审核。**只批准方案设计，不批准自动安装、部署、修改生产环境或启动策略搜索。**
> 审计基准：Phase 0 报告 HEAD `cdef50d`（2026-11-04）。本方案写作时复核：HEAD 仍为 `cdef50d`，工作树干净，`freeze.json` 的 `freeze_time_utc` 仍为 `null`，前瞻样本仍为 0。
> 写作过程只读：未安装软件包、未改代码与配置、未跑回测、未连交易接口、未启动新服务、未改运行中 cron。

## 结论先行（大白话）

1. **先建实验室，再开自动研究。** 现在只有散落的引擎和 2 个 cron，没有登记、没有统一验证器、没有沙箱。直接开自动循环，等于让一台没有刹车的机器去碰运气。本方案把“基础设施验收通过”作为开闸的硬门槛，分阶段放权（见 §7.5）。
2. **每天跑任务，不等于每天出策略。** 每天只做健康检查、数据缺口记账和静默积累；策略按周出，每周最多 3 个假设。3 个全失败时不补新假设，先写失败分析，下一轮必须引用失败教训并证明实质不同。空轮（0 个合格假设）是合格结果，不是事故。
3. **v1.0 的三个家族和 TR-3 单轨全部作废。** TAE、TR-3、②、CA-1、P4 及其他已否决版本退出候选池、永久归档，不得改名换皮复活。未在 v1.1 点名的旧候选（C5、MR-1、SA-1、TR-1、P1/P2/P3、OSS 实验、VO-2）同样暂停，不自动带入新循环，重新进入须按新协议重新登记并证明实质区别（见 §1.3）。
4. **每周预算是硬上限，不是目标。** 每周最多 20 次正式实验，超了调度器直接停轮，不自动加资源。预算数字是本方案的提议值，须你批准（见 §9）；API/LLM 花费目前没有计量手段，开闸前必须先有计数方法。

## 0. 节奏铁律：积累知识的研究员，不是自动化过拟合机器

本节是贯穿全方案的最高约束，任何模块设计不得违反。来源：v1.1 §3–§4，以及你 2026-11-04 12:18 的补充指令。

| 规则 | 内容 | 落到哪里 |
|---|---|---|
| R-节奏-1：无日产出 quota | 每天运行研究任务 ≠ 每天必须产出新策略。每日任务只限：系统健康检查、数据缺口记账、观测器静默积累、知识库维护。每日不得以“今天没出策略”为由启动新假设 | §3 任务协议、§10 每日任务清单 |
| R-节奏-2：每周最多 3 个假设 | 每轮（自然周）最多提出 3 个候选假设。3 个是上限，不是任务量；筛选中 0 个合格时本轮为“空轮”，只出筛选说明，不强行凑数 | §3、§6 计数器、§9 预算 |
| R-节奏-3：失败先分析，后开新轮 | 一轮 3 个假设全部失败时，下一轮不得立即开始。必须先完成：每个假设一份失败备忘 + 一份合并教训笔记，记入知识库；下一轮假设必须引用相关失败条目并写明实质区别。禁止“失败→立刻生成 30 个新假设碰运气” | §3 阶段 6、§6、§8 启动条件 |
| R-节奏-4：失败是资产 | 失败实验永久保留，失败原因、代码版本、数据版本、结果四件套缺一不可。知识库的失败模式条目与成功证据同等重要；周报必须单列“本周学到了什么（失败）” | §6 知识库、§5 验证器、周报模板 |
| R-节奏-5：无无限循环 | 无自动重试放大、无参数循环微调、无“再跑一次看看”。任何重复运行须有新预注册记录与新实验 ID；同一预注册的重复运行只算 1 次正式实验之外的复现运行，并标注 | §3、§6 |
| R-节奏-6：分阶段放权 | 基础设施验收前不开放自动研究权限；验收后先跑 1 轮有人监督的试运行，再逐步放开到每周自动（见 §7.5 三阶段）。每阶段放权都须你单独批准 | §7.5、§8 |

## 2. 缺失组件的开发优先级

按 v1.1 §7 的顺序，1 为最高。顺序的理由：**登记与快照是后面一切的证据地基；验证器与沙箱是开闸前的安全前提；调度器与周报是最后的自动化外壳。** 顺序不得倒置（例如不得先建调度器再补登记）。

| 优先级 | 组件 | 现状 | 建什么（最小必要） | 前置依赖 |
|---|---|---|---|---|
| 1 | 统一实验登记与日志 | 无；结论散在文档与对话里（Phase 0 缺陷 D4） | 登记表 schema + 只追加 ledger + 实验 ID + 计数器（见 §6）；SQLite + Markdown 双写，SQLite 为准 | 无（先行） |
| 2 | 数据质量检查与不可变快照 | 除 C5 外无哈希/版本（D5）；观测器 NPZ 无 SHA256 manifest | 质量门（完整性/时间戳/缺口记账）+ 快照 manifest（SHA256 + 来源 + 窗口）+ 只读冻结目录 | 1（快照须登记） |
| 3 | 回测引擎可信度验证 | B1/C5 两套专属引擎，无通用内核，无统一成本函数（D7） | 通用内核提取 + 对账测试 + 统一成本函数 + 未来函数/未收盘 bar 自动化检查；先验证、后通用化 | 1、2（对账须用已登记快照） |
| 4 | 独立验证器 | 检验方法散在各报告，无统一模块；最终测试集不存在（D6/D12） | 见 §5：划分门禁、安慰剂、基准、成本压力、敏感性、多重检验、尾部评估；测试集随冻结流程新建并上锁 | 1、2、3（验证对象须是已登记的冻结版本） |
| 5 | Codex 执行沙箱 | 无容器/隔离配置；Codex 配置目录近乎为空（D11） | 见 §7：workspace-write 沙箱 + 断网 + 只读根限制 + 资源上限 + 审计日志；先验证隔离有效，再接活 | 1（任务单须登记） |
| 6 | 研究调度器 | 只有 2 个 cron，无统一调度、无预算计数、无防重入 | cron 承载的 v1 调度器：任务队列、计数器、失败重试上限、防重入、每周汇总触发；守护进程化另议 | 1、5（调度器须能读计数器、发沙箱任务） |
| 7 | 自动研究报告 | 有 Markdown 报告传统，无统一模板、无自动产出 | 周报模板（§3 阶段产物 + 失败教训 + 预算消耗 + 下轮建议）+ 每日健康状态（只读检查结果） | 1–6（周报内容全部取自登记表，不得手写数字） |

并行说明：优先级 1–2 的模板与 schema 工作可与 3 的对账测试设计并行；但**任何新策略实验**须等 1–5 全部验收通过（见 §8 启动条件）。

## 3. 自主研究 Agent 的任务协议

### 3.1 角色与权力边界

- Research Agent（MUSE）：自主选择研究主题、提出假设、制定实验、解释结果、规划下一轮。**权力止于**：不得控制最终测试集，不得修改验证器通过标准，不得批准前向模拟，不得扩大权限与预算，不得删除/修改档案。
- Code Agent（Codex）：只接书面任务单（见 §3.3），只写指定范围的代码与测试，只在沙箱内运行。
- Validation Engine：独立裁决，通过标准预先冻结，阈值变更须用户批准 + 版本号升级。
- 用户：每周审核一次（约 20–30 分钟，看周报与证据）；前向模拟、预算变更、规则变更须单独批准。

### 3.2 状态机（v1.1 §3 的执行版）

```
IDEA → SCREEN → SPEC → BUILD → TEST → VALIDATE → ARCHIVE / FORWARD_REQ
  ↑        │        │        │        │           │
  └────────┴────────┴────────┴────────┴── 失败分析 ──┘
  （任一阶段失败都进 ARCHIVE + 失败备忘，不得跳过）
```

- IDEA：提出假设，六要素齐全（收益来源、机制、所需数据、失效条件、与失败策略的实质区别、可证伪设计）。缺一项不得进入 SCREEN。
- SCREEN：按 §3.4 五项优先标准打分 + 指纹查重；每轮最多 3 个通过 SCREEN；0 个通过即为空轮。
- SPEC：实验预注册（见 §3.5），生成唯一实验 ID 并冻结；冻结后规则文本一字不改。
- BUILD：Codex 按任务单实现纯信号函数 + 单元测试；须通过数据质量检查与未来函数检查才能进入 TEST。
- TEST：研究集内有限探索，**所有**尝试记录（含失败与中间版本），不得只保留盈利版本。
- VALIDATE：冻结版本交独立验证器（见 §5），验证器只读冻结产物。
- ARCHIVE：未通过者自动归档 + 失败备忘（见 R-节奏-3）。
- FORWARD_REQ：通过验证者生成前向模拟申请，**须用户批准**才进入前向；申请本身不是批准。

### 3.3 任务单（Task Order）格式

Codex 只接任务单。任务单即登记表中的一行 + 一个 JSON 文件，字段如下（缺字段不予执行）：

| 字段 | 说明 |
|---|---|
| `task_id` / `experiment_id` | 任务与实验唯一 ID（见 §6） |
| `goal` | 一句话目标（实现哪个 SPEC 的哪部分） |
| `scope_files` | 允许读写的文件/目录白名单（超出即拒绝） |
| `forbidden` | 禁区：冻结目录（只读）、`.env`/密钥文件、交易接口、生产 cron 配置、验证器阈值文件 |
| `spec_ref` | 预注册文件路径 + 内容哈希 |
| `acceptance` | 验收标准：单元测试清单、对照测试（同一输入同一输出）、未来函数检查项 |
| `budget` | CPU/内存/时间上限（见 §9） |
| `approver` | 任务单批准人（已批计划内由计划批准覆盖，计划外须单独批准） |

### 3.4 筛选标准（SCREEN 打分，须留痕）

优先选择：经济逻辑清晰、数据可可靠获取、交易成本可估计、实现复杂度适中、与既有失败研究有实质区别。每项 0/1/2 分，总分与分项得分记入登记表；低于门槛（提议：总分 < 6/10 或“实质区别”= 0）不得进入 SPEC。门槛值本身须在方案批准时定，运行中不得由 Research Agent 自行下调。

### 3.5 预注册（SPEC）必填项

策略规则、研究标的、历史交易池、参数及搜索范围、数据划分、费用与成交模型、比较基准、主要评价指标、淘汰条件。另加：数据快照 ID、成本函数版本、随机种子、预期样本量下限（样本量不足时验证结论只能为 INCONCLUSIVE，不得为 PASS）。

### 3.6 失败分析协议（R-节奏-3 的执行版）

每份失败备忘须含：触发的淘汰条件原文、成本分解（毛收益/手续费/滑点/资金费各多少）、失败归因（机制证伪 / 成本淹没 / 样本不足 / 实现问题，四选一 + 证据）、保留的知识条目 ID、下轮须避开的坑。备忘由 Research Agent 起草，记入知识库；合并教训笔记由周报承载。

### 3.7 每日任务清单（无产出 quota）

每日 cron 只做：① 两项现有 cron 的健康检查（观测器缺口、平仓推送静默状态）；② 数据快照新鲜度与缺口记账；③ 登记表与计数器一致性自检；④ 沙箱与门禁状态自检。输出为每日健康状态（简短），**不产生新假设、不启动新实验**。每日任务发现异常时只记录与告警，不自动修复生产配置。

## 4. Codex 与回测引擎的数据交互格式

设计原则：**Codex 只产生信号，引擎只消费信号；结果只由引擎产生，Codex 不得触碰结果文件；格式沿用已有列名与键名，不发明新方言。**

### 4.1 交互序列

```
SPEC.json（冻结） ──► TaskOrder ──► Codex（沙箱）
                                        │ 产出：signal.py + test_*.py
                                        ▼
                              引擎准入检查（数据质量 + 未来函数 + 单元测试）
                                        │ 通过
                                        ▼
                              Backtest Engine（读快照 + 成本函数）
                                        │ 产出：trades.csv + results.json
                                        ▼
                              Validation Engine（只读冻结产物）
```

Codex 与引擎之间**没有**直接函数调用：Codex 产出文件，引擎以文件为界读取。Codex 运行结束后沙箱即销毁，不得保留进程。

### 4.2 格式定义

**（a）预注册文件 `SPEC.json`**（冻结后内容哈希锁定）：

```json
{
  "experiment_id": "EXP-20261109-001",
  "hypothesis_id": "HYP-20261109-01",
  "rule_text": "入场/出场规则的自然语言原文（与代码一一对应）",
  "universe": ["ETHUSDT"],
  "history_pool": {"start": "2020-01-01", "end": "2025-10-17", "tradable_at_time": true},
  "params": {"name": "donchian_n", "values": [20], "search_range": null},
  "split": {"research": "2020-01-01/2023-12-31", "validation": "2024-01-01/2025-10-17", "final_test": "HELD_BY_VALIDATOR"},
  "cost_model_version": "cost-v1",
  "benchmark": ["placebo", "buy_hold_same_basket", "cash_R"],
  "primary_metric": "net_R_per_trade",
  "kill_lines": ["K-1: validation net R <= 0", "K-2: bootstrap 95% CI contains 0"],
  "snapshot_id": "SNAP-20261109-001",
  "seed": 20261109,
  "min_sample": 30
}
```

要点：`final_test` 字段只能写 `HELD_BY_VALIDATOR`，不得写具体窗口（窗口由验证器掌握）；`params.search_range` 为 null 表示 SPEC 阶段已固定参数，研究集内不得扩大搜索。

**（b）信号函数 `signal.py`**（Codex 产出的唯一策略代码）：纯函数，签名固定：

```python
def signals(bars) -> list[dict]:
    # bars: 已收盘 bar 列表（dict 含 open/high/low/close/volume/close_time_utc），
    #       只读，不得访问 bars 之外的任何数据，不得访问未来 bar。
    # 返回：[{"bar_time_utc": ..., "direction": "long|short|flat",
    #         "signal_id": ...}, ...]
```

约束：信号函数不得读文件、不得联网、不得读环境变量、不得 import 回测引擎；违反者准入检查直接拒绝。

**（c）逐笔表 `trades.csv`**（引擎产出，沿用 B1 列名）：`seq_b0`、`window`（research/validation/final）、`dir`、`entry`、`stop`、`exit_time`、`exit_px`、`exit_reason`、`base_gross`、`base_fee`、`base_funding`、`net_R`。成本分解三列强制保留，不得合并。

**（d）结果文件 `results.json`**（引擎产出，沿用 C5 键名）：`run_at_utc`、`seed`、`window`、`tiers`（成本三档）、`buy_hold`、`R`（无风险基准值与来源日期）、`equity`（权益序列或其哈希）、`n_trades`、`mean_net_R`、`ci_95`、`max_drawdown`、`kill_line_results`。`R` 与 `buy_hold` 须同时报告，不得只报策略收益。

**（e）数据快照 manifest `snapshot.json`**：`snapshot_id`、`source`（URL/接口 + 访问时间戳）、`symbols`、`start`/`end`、`n_bars`、`sha256`（数据文件）、`gaps`（缺口记账）、`tradable_pool_note`（历史可交易集合的说明，不得用当前存活列表代替）。快照文件本身只读，任何复用须引用 `snapshot_id`，不得复制后改名。

**（f）任务单与结果回执**：Codex 回执只含 `task_id`、`files_changed`（白名单内）、`tests_passed`、`duration`；**不含**任何收益数字。收益数字只存在于引擎产出的 `results.json` 中，从源头上断开“Codex 为结果负责”的链路。

### 4.3 版本与兼容

- 格式版本号（`format-v1`）写入每个文件头；格式变更须用户批准 + 版本号升级，旧实验按旧格式封存、不迁移重算。
- 数据存储：先用现有 JSON/CSV/NPZ 格式（已验证路径）；Parquet/DuckDB 待 §9 批准安装后再引入，引入时只加新快照格式、不改历史快照。

## 5. 独立验证器的设计

### 5.1 独立性（机制级，不是口头级）

- 验证器是独立模块/独立目录，代码与 Research Agent 的代码物理分离；验证器阈值文件 Research Agent 只读，Codex 禁区。
- 验证器**独占**最终测试集：测试集数据文件 Research Agent 与 Codex 均不可读（目录权限 + 沙箱只读根排除 + 访问日志）。Research Agent 只知道测试集的存在与样本量区间（用于 `min_sample` 判断），不知道具体窗口与内容。
- 验证器只接受“冻结产物”（SPEC 哈希 + 信号代码哈希 + 研究集结果），不接受口头规则、不接受事后补写的 SPEC。
- 验证器裁决一经作出即记入登记表，Research Agent 不得要求重验同一冻结版本；重验须新实验 ID + 新预注册。

### 5.2 验证流程（冻结后依次执行，任一步 FAIL 即整体 FAIL，不得跳步）

| 步骤 | 检验 | 通过标准（预注册，不得事后改） |
|---|---|---|
| V1 | 完整性 | SPEC 哈希一致、代码哈希一致、快照哈希一致、研究集结果可复现（同一输入同一输出） |
| V2 | 泄漏检查 | 未来函数扫描（信号函数只用已收盘 bar）、时间戳连续性、训练/验证窗口无重叠、标签/持仓期重叠处有时间隔离 |
| V3 | 时间序列样本外 | 验证窗口（预先分界）净 R、样本量、Bootstrap 95% CI；CI 含 0 即 FAIL |
| V4 | Walk-forward | 滚动/扩展窗口复核，窗口数与步长预注册；多数窗口为负即 FAIL |
| V5 | 基准比较 | 三重基准：随机方向安慰剂、买入持有同篮子、现金 R；须同时优于三者（安慰剂看百分位，买入持有看风险调整后，现金看经济门槛） |
| V6 | 成本压力测试 | 成本三档全过；最高成本档仍为正才算 PASS，中间档为正只能算 INCONCLUSIVE |
| V7 | 参数稳健性 | 预注册邻域内参数扰动，结论不变；单点参数最优即 FAIL（过拟合嫌疑） |
| V8 | 多重检验与选择偏差 | 全量尝试次数记入 multiplicity 账本；报告选择偏差调整后的显著性；只报最优版本不报尝试次数即 FAIL |
| V9 | 回撤与尾部 | 最大回撤、尾部集中度（最大 5 笔贡献占比）、连续亏损；超预注册尾部线即 FAIL |

### 5.3 裁决输出

`verdict` 三值：`PASS`（全部步骤通过）、`FAIL`（任一杀线触发）、`INCONCLUSIVE`（样本量不足、数据缺口超限、复现不一致——不得按 PASS 处理，不得重跑同一版本刷结论）。裁决文件含：各步骤数值、样本量、CI、尝试总次数、成本分解、复现命令。**单纯正 R、正 CAGR、高收益率不是 PASS 的充分条件**，V3–V9 任一不通过即不通过。

### 5.4 验证器自身的可信度

- 验证器代码须有单元测试 + 对照测试（用已知 FAIL 的归档版本跑验证器，须判 FAIL；用 C5 已知探索结果跑成本门，须复现区间）。
- 验证器版本冻结：阈值、基准方法、安慰剂种子变更须用户批准 + 版本号升级 + 变更日志；旧版本裁决不追溯重判。

## 6. 实验登记与防重复研究机制

### 6.1 登记表（SQLite 为准，Markdown 为可读副本）

库表（提议 schema，建库时以批准稿为准）：

- `experiments`：`experiment_id`、`hypothesis_id`、`round_id`、`spec_hash`、`code_hash`、`snapshot_id`、`cost_model_version`、`seed`、`status`（IDEA/SCREEN/SPEC/BUILD/TEST/VALIDATE/ARCHIVE/FORWARD_REQ）、`verdict`、`created_at`、`decided_at`。
- `attempts`：每次运行一行（复现运行亦记，标注 `kind=reproduction`），含 `run_at`、`result_hash`、`n_trades`、`mean_net_R`。行只追加，永不删除。
- `multiplicity`：累计尝试次数、累计假设数、累计参数组合数（全局 + 每轮），供 V8 读取。
- `knowledge`：知识条目（见 §6.3）。
- `budgets`：每周计数器（假设数、正式实验数、Codex 调用数、CPU/内存/时间消耗），超限即锁轮。

实验 ID：`EXP-YYYYMMDD-NNN`（按日流水）；假设 ID：`HYP-YYYYMMDD-NN`；轮次 ID：`ROUND-YYYY-Www`（自然周）。ID 一经分配永不复用。

### 6.2 防重复研究（指纹 + 区别声明，双重关）

- **指纹** = `机制关键词 + 标的池 + 数据频率 + 入场规则哈希 + 出场规则哈希 + 成本模型版本`。登记时计算指纹，与全部归档实验比对。
- **命中规则**：指纹完全相同 → 直接拒绝登记；指纹近似（机制相同、仅参数/窗口/标的数量不同）→ 标记 `NEAR_DUPLICATE`，Research Agent 须提交书面区别声明（新机制证据或新数据证据），调度器在声明入档前不予排产。
- **改名检测**：区别声明须逐项对照被指认的归档实验（机制、数据、成本、窗口四项），只改名称/只换窗口/只微调参数的声明视为无效，SCREEN 直接否决。
- **复活禁令**：已归档实验的 SPEC 哈希不得被新实验引用为“同一规则的新证据”；引用旧 SPEC 只能作为失败参照。

### 6.3 知识库（积累型研究员的记忆）

知识条目类型：机制笔记（某现象为何可能/不可能成立）、失败模式（某类假设的典型死法 + 证据实验 ID）、成本事实（某标的/某频率的成本量级 + 测量日期）、数据事实（某数据源的缺口/偏差 + 快照 ID）。每条含：条目 ID、结论、证据链接（实验/快照 ID）、置信度（高/中/低）、最后复核日期。**新假设登记时须填写 `builds_on`（继承哪条知识）与 `differs_from`（区别于哪条失败知识）**，空填视为 SCREEN 材料不全。

### 6.4 周报的数据来源

周报数字**全部**取自登记表（SQL 查询结果），不得手写、不得引用对话记忆。周报须含：本轮假设数与空轮说明、正式实验数与预算消耗、PASS/FAIL/INCONCLUSIVE 清单、失败教训（R-节奏-4）、知识库新增条目、下轮建议（须引用失败备忘）。

## 7. 安全隔离与权限方案

### 7.1 隔离层次（技术措施，不是提示词约束）

| 层 | 措施（方案提议，实施须另批） | 验证方法 |
