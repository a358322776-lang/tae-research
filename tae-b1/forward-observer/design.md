## 2. 检测口径（逐字复用 B1 Phase-A，不发明）

来源：`rules-v0.1-frozen.md` + `levels_pass.py`（候选生成）+
`events_census.py`（Phase A 状态机）+ `ordered_outcomes.py`
（收复后窗口先后顺序结局）。只读复用 `key_levels.py` /
`b1_lib.py`，绝不修改它们。

- 每根 15m 收盘时，用 trailing 400 根重算 `find_levels`（阻力归簇
  链式容差 0.35×ATR、守住检验推离 ≥1×ATR 且 4 根内无收盘越界、
  MIN_TOUCH=3、STALE_BARS=96，去重规则同原模块）。
- 候选：单根收盘穿越（多头 close[j-1] <= bhi < close[j]，空头镜像）
  且 1H 严版大趋势同向（B1 指针法：1H 收盘 <= 该 15m 收盘、
  摆动点 idx <= p-3、≥60 根、每级 ≥0.5×ATR(1H)）。
- P3：每方向每根只取最贴近现价的一条带（多头取最大 bhi，空头取
  最小 blo），其余记 `p3_shadowed`；与同方向活跃序列带重叠则记
  `overlap_active` 并跳过。未成序列候选记入 `skipped.csv`。
- 序列状态机（每根先更新活跃序列、再接入本根新候选）：
  远沿收盘穿越作废 → 触碰标记（极值与带相交）→ 收盘收复 →
  b0+48 根过期；同根触碰+收复允许（该根不得是 b0）。
- E 信号（仅描述性特征）：收复后 3 根已收盘 5m 内是否出现顺方向
  六种 E 信号；第 3 根 5m 恰遇下一根 15m 收盘穿越远沿时记
  `coincident_void`。不算触发价、不算成交、不算杠杆。
- 收复后 N=48/96 窗口先后顺序结局（审查口径）：摆动事件时刻 =
  确认根收盘（摆动 bar + 2 根）；跌穿事件时刻 = 首根收盘穿越
  远沿；A 先摆动 / B 先跌穿后摆动 / C 仅跌穿 / D 两者皆无 /
  T 同根 tie（单列不并入）。
- I4-A 失效：评价在 1H 收盘上做，盘中不算，吸收态；**两种种子
  读法同时记录**：M（普查实现：截至 b0 全部已确认摆动极值的极值）
  与 L（文档本意：截至 b0 最新已确认摆动极值），确认时序相同。
  审查已证实两者行为完全不同，冻结时再选——本系统不替选。
- I4-B 重检：v0.2 严格早于法（1H 收盘 < 事件时刻，摆动点
  i+k ≤ 最后可用索引）；t0 与收复根落入同一 1H bar 时记
  `merged_into_reclaim`。原始 1H 收盘序列已存下，替代时刻约定
  可在分析时重算。

## 3. 存储与时间戳（冻结切分规则）

见 `schema.md`（字段字典）。关键规则：

- 原始 K 线：bar 级 append-only（只追加 t 更大的 bar；已存 bar
  永不改写；内容冲突记入 manifest 并保留旧值）。文件以 atomic
  replace 写入，防崩溃撕裂。
- 事件时间线 `timeline.jsonl`：append-only，每行一次状态变迁。
- `ledger.csv`：当前快照（行永不删除；状态字段随演化更新）。
- 每条序列带四个时间戳：`b0_time_utc`（事件时间）、
  `outcome_time_utc`（结局 bar 时间）、`outcome_resolved_at`
  （系统记录结局的墙钟时间）、`created_at` / `updated_at`。
  冻结切分规则：`freeze.json` 中的 `freeze_time_utc` 一旦由用户
  冻结操作写入，分析时以 `b0_time_utc < freeze_time_utc` 为
  冻结前探索数据、`>= freeze_time_utc` 为冻结后验证数据；
  在冻结前，本系统产生的一切数据均为探索数据，不得当作验证。
- 1H 摆动点清单：由存储的 1H 收盘序列 + `swings_tie`（k=2）
  在分析时重算（与普查同一函数）；两种种子读法下的 Theta 取值
  在 ledger 中按 b0 / 收复 / 失效时刻分别存下。

## 4. 围栏清单（硬性，见 check_fences.py 验证结果）

- 不写扫描器 state、执行器目录、任何推送 cron 或信号文件。
- 不调用下单、撤单、改杠杆等任何交易接口；唯一网络目标是
  公开 klines 镜像（无密钥、无签名、无账户操作）。
- 不读取 `.env` / `.env.live` / 任何密钥文件；不读 B1、扫描器、
  执行器的任何文件（只读复用 `key_levels.py` / `b1_lib.py`
  两个纯函数模块，且禁止写字节码缓存）。
- 不向 WhatsApp 或 App 发任何消息；cron 只写 `state/observer.log`。
- 不修改 B1 的任何文件；全部写路径只在 `forward-observer/` 内。
- 围栏检查（`check_fences.py`）：静态（可执行代码无禁用令牌、
  无非镜像 URL、import 白名单、写路径全在目录内）+ 动态
  （一次实际运行前后对交易相关树的 mtime 快照对比，外部 0 变动）
  + 哨兵文件（candidates.jsonl、stitched 缓存、两扫描器）mtime
  未动。2026-10-27 实测：**VERDICT: PASS**（见 `fence_check.txt`）。

## 5. 运行方式

- 幂等：每次运行从上次存下的最后一根 bar 起续拉；无新 bar 时
  直接退出（0 新序列、0 结算），重跑不产生重复记录。
- 缺口检测＋回补：存储前后检查时间戳差分；缺口用公开历史
  回补（可拉取，漏跑可自愈）；补不上的缺口记入 manifest
  `gaps_unfilled`，不静默跳过。
- cron：每 15 分钟静默运行一次（命令见 §6），只写
  `state/observer.log`，无用户侧输出。
- 首次运行 warmup：45 天历史（保证 trailing 400 根窗口完整）；
  前约 4 天为 burn-in（下标 <399 的 bar 不产生 b0，与普查
  range(399, n) 行为一致）。
- 性能：45 天干跑约 32 秒；常规每 15 分钟运行处理 1 根新 bar，
  约 4 秒。

## 6. cron 方案

- 调度：每 15 分钟（`*/15 * * * *`）。
- 命令：`PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 <BASE>/observer.py
  --run --quiet >> <BASE>/state/observer.log 2>&1`
  （`--quiet` 抑制 stdout；stderr 仍进日志；无用户侧输出。）
- cron id 与下次运行时间见交付汇报（由 cron 工具返回）。
